## Files touched
- [src/extension/codelens/roleCategory.ts](../../src/extension/codelens/roleCategory.ts) — new. `classifyRoleTag()` buckets an arbitrary `role_tag` string into one of 7 fixed categories (`handler`, `validator`, `persister`, `middleware`, `test`, `config`, `utility`) via case-insensitive keyword substring match, first-match-wins, falling back to `generic`. Single source of truth for both new surfaces: also exports `categoryEmoji()`/`categoryIconFile()` and the `pending` (not-yet-cached) constants, so CodeLens and gutter can never disagree about a function's category.
- [src/extension/codelens/roleCodeLensProvider.ts](../../src/extension/codelens/roleCodeLensProvider.ts) — new. `RoleCodeLensProvider implements vscode.CodeLensProvider, vscode.Disposable`. Resolves every function in a document (`resolveAllFunctions`, same path hover/save-reindex/background-index already use), looks each one up in the cache (never generates), and renders one lens per resolved function: `<emoji> <role_tag>` on a hit, `○ not indexed yet` on a miss. Every lens uses `command: ''` (empty command id) — the standard non-clickable-label CodeLens idiom — so no new command needs registering to satisfy "zero interaction." Exposes `refresh()` → fires `onDidChangeCodeLenses`.
- [src/extension/codelens/roleGutterDecorations.ts](../../src/extension/codelens/roleGutterDecorations.ts) — new. `RoleGutterDecorationManager implements vscode.Disposable`. One `TextEditorDecorationType` per category (8) plus one `pending` type (9 total), each pointing at a `media/roles/*.svg` icon. `refreshAll()` re-walks every `vscode.window.visibleTextEditors`, resolves + looks up + classifies exactly like the CodeLens provider, and calls `editor.setDecorations()` per category. Also listens to `onDidChangeVisibleTextEditors`/`onDidChangeActiveTextEditor` directly (decorations have no `CodeLensProvider`-style pull API, so this class owns its own redraw triggers).
- [media/roles/*.svg](../../media/roles/) — new, 9 files: 7 solid-color filled circles (one per real category), `generic.svg` (solid light-gray fallback), `pending.svg` (dashed hollow outline — visually distinct from `generic`'s solid fill, so "uncategorized but explained" never looks like "not yet indexed").
- [src/extension/cache/explanationCache.ts](../../src/extension/cache/explanationCache.ts) — added `onDidWrite()`/a private `writeListeners` set, fired at the end of `write()`. Deliberately a plain listener-set, not a `vscode.EventEmitter` — this class has never imported `vscode` (pure `better-sqlite3` storage layer) and there's no reason to start now just for this. This is the one new mechanism the session needed (design question 3): every write, from any of the four call sites that flow through `generateAndCache()` (hover miss, save-reindex, background-index, manual refresh), now notifies through exactly one place.
- [src/extension/extension.ts](../../src/extension/extension.ts) — registers `RoleCodeLensProvider` (`vscode.languages.registerCodeLensProvider`) and `RoleGutterDecorationManager` unconditionally in `activate()` (Core Rule 6, same pattern as hover/panel). In `startIndexing()`, once `explanationCache` exists, subscribes both surfaces to `explanationCache.onDidWrite()` and fires one initial `refresh()`/`refreshAll()` for editors that were already open before trust was granted. `deactivate()` disposes the new manager and clears both module-level vars.

## Decisions made

### Design pass (per the session instructions, answered before implementation)

1. **Role-tag → visual category mapping:** a small ordered keyword-bucket list (`roleCategory.ts`), not a schema/prompt change. 7 real categories chosen to cover plausible model output for common function shapes (route/callback handlers, validators, DB/store persisters, middleware/interceptors, tests, config/setup, generic utils) plus a `generic` fallback for anything unmatched. Kept deliberately small — this is a display-layer heuristic over free-form text, not a taxonomy the model is aware of, so it doesn't need to be exhaustive, just non-embarrassing on typical output. `role_tag` itself (the actual cached string) is always still what's *shown* — the category only ever picks an icon/emoji.
2. **Cache-miss behavior:** the two surfaces never generate. A resolved-but-uncached function gets a distinct neutral placeholder (`○ not indexed yet` CodeLens text; a dashed hollow-outline gutter icon, visually distinct from every filled category dot including `generic`). A function VS Code's own symbol provider can't resolve at all never enters either provider's per-function loop in the first place (both walk `resolveAllFunctions`'s output directly) — so it gets no lens and no decoration, full stop. That absence *is* the distinction design question 2 asked for: "pending" only ever describes something the extension can see and is choosing not to guess about.
3. **Live refresh:** `ExplanationCache.onDidWrite()` (see "Files touched" above) is the one new notification path, and both surfaces subscribe to the exact same event — no second mechanism, per the instructions. `RoleCodeLensProvider.refresh()` just fires `onDidChangeCodeLenses`, which makes VS Code re-call `provideCodeLenses` for visible documents (cheap: a `resolveAllFunctions` + N cache lookups, same cost hover already pays per-hover). `RoleGutterDecorationManager.refreshAll()` re-walks `vscode.window.visibleTextEditors` directly, since decorations have no VS Code-native "these are stale, re-pull" callback the way `CodeLensProvider` does.
4. **Trust gating:** identical pattern to every other surface in the codebase (hover, panel, save-reindex, background-index) — both providers register unconditionally in `activate()`; their `getWorkspaceRoot()`/`getCache()` getters resolve to `undefined` until `startIndexing()` completes under trust, and both providers render nothing (empty lens array / all decoration ranges cleared) in that state.

### `command: ''` instead of a registered no-op command
Considered registering a real `lucidhover.codeLensNoop` command (or reusing an existing one) so every `vscode.CodeLens` has a "real" command object. Went with `command: ''` (empty command id) instead — a well-established VS Code idiom for label-only, non-interactive CodeLens text — because it needs zero new command-palette surface area and matches the spec's explicit "zero interaction" requirement for the role badge more directly than a command that technically does something (even a no-op) when clicked.

### `pending` as a ninth decoration type, not a missing one
Could have chosen to render nothing at all for an uncached-but-resolved function (skip the range entirely, same as an unresolvable one). Rejected: design question 2 explicitly asked these to be distinguishable, and a completely silent gutter for "we see this function, we just haven't explained it yet" is indistinguishable from "this line was never a function at all" — the exact ambiguity the question flagged. A dashed hollow icon (vs. every real category's solid fill) makes the state legible without adding a text label to the gutter (which the API doesn't support anyway — gutter icons are image-only).

### Single category-mapping module reused by both surfaces
`roleCategory.ts` has no `vscode` dependency and no side effects — pure string-in, category-out. Both `roleCodeLensProvider.ts` and `roleGutterDecorations.ts` import from it rather than each defining their own bucket list, directly per the instructions' "reuse it for both surfaces rather than building two" — applied to the classification logic as well as the notification path.
