## Decisions made

### Cache ownership decision (the ambiguity this session was asked to resolve)
Adopted the recommended split with one refinement:
- **Extension host (TS) owns the SQLite database** via `better-sqlite3`, in `src/extension/cache/`. It performs all reads/writes.
- **The sidecar computes `context_hash` and `context_tier`** as part of its `generate_explanation` response (`sidecar/cache/hashing.py`), since only it has the ranked call-graph data those require. It never touches SQLite.
- **Refinement: `fn_hash` is computed by the extension host, not the sidecar**, contrary to the session prompt's literal suggestion. Reason: the manual test requires the sidecar to be invoked on the *first* hover only — a second hover of the same unchanged function must hit the cache with zero sidecar contact. That's only possible if the cache lookup key (`fn_id` + `fn_hash` + `model_id`/`embedding_model_id`/`prompt_version`) is fully computable *before* any sidecar round trip. `fn_hash = sha256(fn_source)` needs only the live document text, which the hover provider already has from its existing document-symbol resolution — so computing it in TS costs nothing and is what makes the sidecar-skip-on-hit behavior possible at all. `context_hash`, by contrast, genuinely needs the sidecar's ranked graph and is only known *after* a miss, so it stays sidecar-side and is deliberately excluded from the pre-sidecar lookup predicate.
- **File-ownership table conflict, not resolved, flagged for a human:** [CLAUDE.md](../../CLAUDE.md)'s file-ownership table lists `sidecar/cache/` as the "Cache layer" owner path, which predates this decision and doesn't fit it (the actual SQLite code is TS, under `src/extension/cache/`; `sidecar/cache/` ended up holding only the sidecar-side `context_hash` helper, which is cache-*adjacent* support code, not the cache layer itself). Did not edit CLAUDE.md's table myself since it's project-instruction content, not this session's output — flagging here so a human can update that row (suggest: `Cache layer | src/extension/cache/` (SQLite, cache-key logic); the `sidecar/cache/` path becomes just "sidecar-side context-hash helper" or gets merged into the sidecar/repomap row).

### Cache-key formula interpretation
Core Design Decision #2 says `cache_key = hash(fn_source + context_hashes + model_id + embedding_model_id + prompt_version)`, with "context_hashes" plural (per-chunk). Implemented as two hash layers: `context_hash` (sidecar) = `sha256(sorted per-chunk hashes joined)`, collapsing the plural into one value; `cache_key` (TS) = `sha256(fn_source + context_hash + model_id + embedding_model_id + prompt_version)`. This avoids re-transmitting/re-hashing the full context text twice (once for `context_hash`, again inside `cache_key`) while still making `cache_key` change whenever any chunk changes, since `context_hash` itself changes. Documenting as an interpretation, not a deviation, since the formula doesn't specify the exact chunk-hash composition mechanism.

### Function-identity resolution across VS Code symbols vs. tree-sitter tags
The hover provider resolves functions via `vscode.executeDocumentSymbolProvider` (built-in JS language service); the sidecar's repomap graph is keyed on tree-sitter def tags. Their line numbers don't always agree (e.g. `const foo = () => {}` — the built-in symbol provider's range may start at `const`, tree-sitter's def span starts at the identifier/arrow-function node). `generate_explanation`'s `_find_def_tag` resolves `(rel_fname, name, line)` by matching `name` within the file and picking the tag whose `start_line` is closest to the given `line`, rather than requiring an exact match. `fn_id` (the TS-side cache row key) still uses VS Code's own line number — it only needs to be stable across repeated hovers of the same unchanged function, not to agree with tree-sitter.

### Stub explanation content
`generate_explanation` returns real caller/callee names (from the actual ranked graph) inside a templated-but-fake `one_liner`/`why_it_exists`, rather than fully hardcoded field values, so the plumbing test (does the JSON actually reflect real per-function data, not one static blob for every function) is meaningful. `role_tag` is a fixed `"Function"` placeholder — no role classification exists yet, that's part of real generation.

### Cache DB location and lifecycle
`context.storageUri` (workspace-scoped persistent storage), directory created via `vscode.workspace.fs.createDirectory` before opening. Opened only after `SidecarManager.start()` succeeds — cache existing without a working sidecar would be a dead end for cache-miss handling anyway. Disposed via `context.subscriptions`.

### Removed Session 4 scaffolding
Deleted `lucidhover.debugIndexFile` and its `package.json` command contribution — the real hover-to-cache path now exercises the sidecar connection more thoroughly than that command did, and CLAUDE.md's project instructions caution against lingering scaffolding once superseded.
