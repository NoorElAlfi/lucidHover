## Decisions made

1. **Root cause, found via a user-supplied `oddResponses.txt`** listing real generated explanations from real pokerogue where `tint()` and `untint()` (two structurally-similar but distinct methods, one in `src/field/pokemon.ts`, one in `src/field/trainer.ts`) showed byte-identical, obviously-wrong "Calls"/"Used by" lists (`setVisible` repeated 9x, `add` repeated 6x, concatenated with no delimiter). Traced to `sidecar/repomap/graph.py`'s `build_call_graph()`: a call ref resolves to a callee by bare identifier name only (`defs_by_name.get(ref.name)`), fanning out to *every* in-repo definition sharing that name, unconditionally — a deliberate, documented choice mirroring Aider's own approach (the code comment cites it explicitly), correct for PageRank ranking bias but reused as-is for `context.py`'s `get_function_context()`, whose output is fed directly into `sidecar/generation/prompt.py`'s "Known callers"/"Known callees" as asserted fact. `tintSprite.setVisible(true)` (a Phaser library call) was resolving as "known" to call an unrelated `Dropdown.setVisible()` UI method and a `MysteryEncounterIntro.setVisible()`, purely by name collision — same mechanism explains the "leads to the same point" pattern the user independently spotted: two different functions calling the same *names* get the exact same fanned-out candidate set regardless of what they actually call.
2. **Design question put to the user rather than guessed** (matching this project's session-39 precedent for real policy tradeoffs): how should an ambiguous name (2+ matching defs) be handled for context/prompt display specifically, given PageRank ranking must stay untouched (Core Rule 3)? Three options were presented — drop ambiguous names from context entirely; prefer same-file matches, drop only if none; keep the fan-out but relabel it as uncertain. **User chose "prefer same-file matches, drop only if none."**
3. **Implementation split ranking from context deliberately.** `rank.py`'s `compute_importance()` is untouched — still runs `nx.pagerank(graph, weight="weight")` over every edge regardless of `confident`, confirmed by code review to only ever read the `weight` attribute. Only `context.py`'s caller/callee *display* path (which becomes prompt input and report content) filters by `confident`.
4. **A genuine incremental-correctness gap was found and fixed mid-session, not by inspection but by a failing test.** Session 38's incremental design assumes `weight` is purely additive — a file's own edit only ever needs to touch edges incident to that file. `confident` isn't additive: it's a function of a name's *entire* repo-wide candidate set, so adding a same-named def in file Z can flip confidence on a pre-existing X→Y edge where neither X nor Y is Z (exactly the scenario the first version of the duplicate-name test caught: adding a second `validateEmail` in a brand-new third file didn't drop the existing `handlers.js → utils.js` edge's confidence, because neither of Session 38's two edge loops ever revisits edges that don't touch the file being reindexed). Fixed with a third pass, bounded by `affected_names × fan-in(name)` via the same reverse-index (`refs_by_name`) pattern Session 38 already established — not an O(repo) rescan, confirmed by code review. Code review separately noted this third pass does mildly redundant work re-touching `rel_fname`'s own already-correct edges (doesn't filter `ref.rel_fname == rel_fname` the way the second loop does) — a minor, non-asymptotic inefficiency, not fixed, since it doesn't regress Session 38's core guarantee and the fix risked adding complexity for no measurable win.
5. **No `PROMPT_VERSION` bump.** Verified `sidecar/cache/hashing.py`'s `compute_context_hash()` hashes `ctx.callers`/`ctx.callees` content directly (via `_context_chunks`), so any function whose confident caller/callee set changes automatically gets a different `context_hash` and thus a different cache key. This is context *composition* changing (Core Rule 5's `context_hashes` term), not prompt *text* changing (Core Rule 10) — `prompt.py` itself was not touched. Confirmed independently by code review.

## Handoff for next session
- This fix only narrows *display* confidence (context/prompt/report) using a same-file heuristic; it does not add real type/import-based call resolution. A name that's ambiguous with no same-file candidate still shows as "no known callers/callees" even when a real relationship exists but happens to be cross-file — full precision here is explicitly Core Rule 3's post-MVP LSP-based resolution work (Serena's pattern), not something to reach for incrementally.
- If real-repo acceptance-report noise from *other* ambiguous-name patterns turns up later, the mechanism to check first is this same `confident` flag / `_confident_callee_ids` same-file heuristic before assuming a new bug — many generic method names in a large OOP codebase will still legitimately show "no known callers/callees" under this policy, which is the accepted tradeoff, not a defect.
