## Files touched

- [src/extension/sidecar/sidecarManager.ts](../../src/extension/sidecar/sidecarManager.ts) — hardened the existing heartbeat/restart supervision (Session 4 stub, Session 6 real, Session 14's `reason` param), not a new supervision mechanism:
  - Added `restartAttempts`/`givenUp`/`expectedExit`/`currentRecovery`/`restartRetryTimer`/`restartRetrySignal` state and a persistent `vscode.StatusBarItem`.
  - `restart(reason, resetAttempts = false)` is now the single public entry point for every trigger (heartbeat threshold, unexpected `child.on('exit', ...)`, manual "Restart Sidecar", and — via `extension.ts` — the very first startup attempt). It never throws; resolves `true`/`false`. It de-dupes against `currentRecovery`: a concurrent caller wakes an in-flight loop early (via `cancelPendingRetry()`) and awaits its real outcome instead of either no-op'ing or spawning a competing loop.
  - New private `runRecoveryLoop(reason)`: loops `teardown()` → `start()`; on failure, exponential backoff (2s/4s/8s/16s/30s, `MAX_RESTART_ATTEMPTS = 5`) via a cancellable `sleep()`; on the 5th consecutive failure, sets `givenUp`, updates the status bar, and shows a one-time `showErrorMessage` toast with a "Restart Sidecar" action.
  - `child.on('exit', ...)` now triggers `restart()` immediately instead of only logging, guarded by `expectedExit` (set by `teardown()` right before it deliberately kills a live child) and a `this.childProcess !== child` stale-closure check.
  - `applyOllamaEndpoint()` now calls `restart(reason, resetAttempts = true)` and returns the resulting boolean.
  - `dispose()` cancels any pending backoff sleep and disposes the status bar item.
- [src/extension/extension.ts](../../src/extension/extension.ts):
  - `startIndexing()` now calls `await manager.restart('initial startup')` instead of `await manager.start()`, dropping the old single-attempt try/catch+toast (the recovery loop's own give-up toast now covers that case too).
  - The `lucidhover.restartSidecar` command now checks `applyOllamaEndpoint`'s returned boolean instead of assuming success; on failure it relies on the recovery loop's own give-up toast rather than showing a second one.

## Decisions made

Answering the five design questions from the session brief, in order:

1. **Backoff and give-up policy.** New `restartAttempts` counter, reset only on a successful (re)start or an explicit manual restart — not on every attempt. Exponential backoff between attempts (2s base, doubling, capped 30s: 2/4/8/16/30s), first attempt always fires immediately. Give up after `MAX_RESTART_ATTEMPTS = 5` consecutive failures (~30s of backoff plus attempt overhead); at that point the supervisor stops auto-retrying entirely and waits for a manual restart. This falls out naturally with no extra "if given up, refuse" guard: once given up, `teardown()` has already killed/cleared the process and no heartbeat timer exists (it's only created inside a successful `start()`), so there is no live trigger left to call `restart()` again spontaneously — only the manual command (or `applyOllamaEndpoint`) can wake it.
2. **User-visible signal, and at what threshold.** A persistent `StatusBarItem` (click → runs `lucidhover.restartSidecar`) stays hidden while healthy, and appears as soon as the *first* attempt within a recovery loop fails and a backoff wait is scheduled — already past the heartbeat's own quiet 3-strike buffer (`HEARTBEAT_FAILURE_THRESHOLD`) for heartbeat-driven triggers, and past the immediate first attempt for exit-driven triggers, so a single crash-and-instant-respawn never flickers it. A `showWarningMessage`-equivalent (`showErrorMessage` with an action button) toast fires exactly once, only at the give-up threshold — the one point auto-recovery has genuinely stopped and needs the user's attention, matching "transient hiccups recover quietly, toast only when something is actually actionable."
3. **React to `child.on('exit')` directly, bounded against restart storms.** Yes — triggers `restart()` immediately rather than waiting for the next heartbeat tick (closing the up-to-120s gap the brief flagged for a mid-generation-call death). Reuses the *same* `restartAttempts`/backoff counter as heartbeat-triggered restarts rather than a separate counter — both are just different triggers into the one recovery loop, and unifying them means an instant-repeated-crash case (e.g. a missing Python module) is still bounded: each attempt costs at least the ~5s `connectWithRetry` timeout, backoff grows between attempts, and the loop gives up after 5 consecutive failures rather than spinning. Guarded by `expectedExit` (set only when `teardown()` itself kills a live child) so a deliberate restart/dispose never misfires as a "crash," plus a stale-closure check (`this.childProcess !== child`) so a delayed exit event from an old process instance can't affect a newer one.
4. **Manual "Restart Sidecar" interaction with the new auto-recovery state.** A manual restart (`applyOllamaEndpoint(url, ...)` → `restart(reason, resetAttempts = true)`) unconditionally resets `restartAttempts`/`givenUp`. Safety while an auto-retry might already be in flight is handled by de-duping on `currentRecovery` rather than a raw reentrancy no-op: if a loop is already running (mid-attempt or asleep in backoff), the manual call wakes it early via `cancelPendingRetry()` and awaits the *same* promise everyone else is awaiting, so there is never more than one live recovery loop and the caller always gets the real eventual outcome (not a guessed one). The woken loop picks up the freshly-reset attempt count and the freshly-updated `ollamaBaseUrl` on its very next iteration.
5. **First-ever startup failure vs. a mid-session crash.** Folded into the same mechanism rather than left as a separate single-unretried-attempt path: `startIndexing()` now calls `manager.restart('initial startup')` instead of `manager.start()` directly, so a first-run hiccup (Python not yet on PATH, Ollama still starting) gets the same backoff-retry-then-give-up treatment and the same give-up toast, not a bespoke one-shot error message. This was a one-line call-site change in `extension.ts` with no control-flow restructuring — `restart()` already tolerates being called against a virgin manager (`teardown()` is a no-op when nothing exists yet).

2. 3. Forced the give-up path: ran a 90-second PowerShell loop that killed the sidecar process the instant it (re)spawned (tight race against the sub-second window between process spawn and the socket/pipe opening — `rpc_server.py`'s `main()` runs `RepoMap.index()` before `_serve_windows`/`_serve_posix`). Some early rounds likely slipped through as successful reconnects (resetting the attempt counter, per the observed non-monotonic kill-gap timing), but the loop eventually won the race five consecutive times. **Expected:** status bar climbs through `restarting (N/5)`, then a `sidecar down` error state plus a one-time toast with a "Restart Sidecar" action once attempt 5 fails, with a working recovery path back out via that action or the command. **Confirmed** — output channel showed attempts escalating up to 5/5 and a `sidecar recovery gave up after 5 attempts` line; the error toast appeared; clicking "Restart Sidecar" (with the kill-loop stopped) produced a clean `sidecar (re)started successfully`, cleared the persistent status bar item, and hover worked again immediately after — closing the loop on design question 4 (manual restart correctly un-sticks a given-up state) as well.
