## Decisions made

1. **`embedding_model_id` is spawn-time config, not a per-`generate_explanation`-request param.** The pre-approved plan said this would "mirror `model_id`" (a request param); implementation changed this once it became clear the sidecar's one-time startup full-repo embedding pass has to pick a model *before* any RPC request exists to carry one. Passing it once at spawn (new 4th argv, alongside the also-new `storage_dir`) and reusing it for every later query removes any risk of the corpus being embedded with one model and a query embedded with another — a silent, hard-to-detect bug if they ever drifted. `MODEL_ID` stays a per-request param since generation genuinely could vary the model per call; the embedding side has no equivalent reason to.
2. **`RetrievedChunk` is a separate parameter, not a new `FunctionContext` field.** Threaded through `generate.py`/`prompt.py`/`hashing.py` on its own rather than added to the frozen `FunctionContext` dataclass in `repomap/context.py`. Keeps `context.py` (and `RepoMap`) free of any Ollama/network dependency — chunking-and-embedding is a real I/O-bound pass, everything else in `context.py` is pure in-memory graph lookup. `context.py` itself was not touched this session.
3. **Chunk size recalibrated from ~40 lines to 12 after live-testing against the real bundled embedding model.** The spec's "~200 tokens/chunk" was implemented first as a ~40-line heuristic (code runs roughly 4-6 tokens/line). Live end-to-end testing against `all-minilm` (pulled this session, with the user's explicit permission) immediately surfaced `{"error": "the input length exceeds the context length"}` from Ollama's `/api/embeddings` on typical 40-line JS chunks — MiniLM-L6's real context window is a hard 256 tokens, smaller than assumed. Binary-searched down against real fixture-repo content (15 lines/691 chars OK, 20 lines/817 chars failed) and settled on 12 lines with margin, then re-verified every chunk in the fixture repo embeds successfully. This is the one place this session's initial design assumption was measurably wrong and corrected against the real model, not just the spec's prose.
4. **Retrieval failures degrade gracefully; generation failures still fail loud.** `_query_retrieved_chunks()` and the startup/reindex embedding passes catch `OllamaError` and continue with an empty retrieved-chunks list (logged as a warning) — retrieval is an additive context tier, and losing it (e.g. the embedding model isn't pulled) must not take down hover/save/refresh, which depend on the sidecar being able to generate at all. This is a deliberate contrast with `ollama_client.py`'s own module docstring ("never silently stub or fall back") and `_handle_generate_explanation`'s existing fail-loud `OllamaError → RuntimeError` re-raise for the actual generation call — that guarantee is scoped to the LLM output the user reads, not to an optional input tier. (Verified live — see "Test status".)
5. **No separate vector-index version marker; `embedding_model_id` alone is the v0 invalidation key** — as pre-approved (design question 3). Matches the existing precedent that `context_hash` captures content, not "which version of the extraction code produced it" (the call-graph tier has no such marker either).
6. **`.gitignore` matching via `pathspec`, file walk reused from `extraction.find_js_files`.** No second file walker; `pathspec.PathSpec.from_lines("gitwildmatch", ...)` handles real gitignore glob semantics rather than a hand-rolled matcher. JS-only scope, same as the call-graph tier (no expansion to other file types this session).
7. **LanceDB lives at `<context.storageUri>/lancedb`**, workspace-scoped as pre-approved. Required reordering `extension.ts`'s `startIndexing()` to compute the storage path before spawning the sidecar (previously computed only for the SQLite cache, after spawn).
8. **The startup full-repo embedding pass runs on a background thread, not inline in `main()`.** Found only by actually running the real extension in VS Code (see "startup pipe/socket ENOENT" under "Blockers / open questions" — this was a genuine bug in what got reported as "complete" above, caught by the user's live test, not by any test in this session's own suite). `VectorStore` gained a `threading.Lock` as a direct consequence, since the background embed pass can now genuinely overlap a same-process `reindex_file`/`generate_explanation` call on the main dispatch thread.

**Resolved: startup pipe/socket ENOENT — the sidecar failed to start every single time in real VS Code.** This session's own "live end-to-end verification" (see "Test status") called `_handle_generate_explanation` and friends directly in a Python script, which never exercises `main()`'s actual startup sequence or `SidecarManager`'s connect logic — so the bug shipped undetected past this session's own testing and was only caught when the user actually opened the project in VS Code and got "LucidHover: failed to start the sidecar process." The LucidHover output channel showed `Error: connect ENOENT \\.\pipe\lucidhover-<pid>-<ts>` right after `[sidecar] embedding repo chunks (model=all-minilm) ...`. Root cause: `main()` ran the full-repo embed pass *before* creating the named pipe/socket, and even the tiny 16-chunk fixture repo's pass (Ollama cold model load + 16 sequential `/api/embeddings` calls) took longer than `sidecarManager.ts`'s `CONNECT_RETRY_ATTEMPTS x CONNECT_RETRY_DELAY_MS` = 5s connect budget — a budget calibrated back when startup was just a sub-second tree-sitter parse. Fixed by moving the embed pass onto a `threading.Thread` so the pipe/socket is created and accepting connections immediately, with retrieval queries against the still-filling `VectorStore` degrading to `call_graph_only` (the same graceful-degrade path already built for an unreachable embedding model) until the background pass finishes. Verified with a standalone timing script mimicking the extension's own connect-retry loop: the pipe became connectable in ~2.5s (well under the 5s budget) regardless of how long the background embed pass took (~45s in one run). Full sidecar suite re-run clean afterward (64 passed, only the pre-existing unrelated failure below remains) and `tsc` clean.
