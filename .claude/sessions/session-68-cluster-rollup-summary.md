## Decisions made

Two design questions were put to the user via `AskUserQuestion` before writing any code, per the session brief's own instruction:

1. **Trigger: a new cursor-anchored command**, not folded into the existing `generateSummaryDocs` command.
2. **Render target: a new docked-panel view mode**, not folded into `docs/wiki/` output. Reuses the existing pinned-panel plumbing via a third `GraphViewPayload.direction` value.

**Mid-session redesign, following a `code-reviewer` finding (see Test status below): the feature was originally one command (`showClusterSummary`) that looked up a cached purpose paragraph and, on a miss, synthesized and cached one right then, before rendering.** The reviewer correctly flagged this as a Core Rule 4 violation: the docked panel's render path has no exception for synchronous generation, unlike hover's cache-miss fallback -- and `summaryDocGenerator.ts`'s session-15 precedent this session's brief cited never actually established such an exception, since that command writes to markdown files on disk and never touches the panel at all. Fixed by splitting into two commands:

- **`showClusterSummary`** is now a genuine pure cache lookup (`lookupClusterPurpose`, zero RPC calls beyond the graph-only `get_blast_radius`) -- the panel's own render/lookup path, exactly like blast radius and execution trace.
- **`synthesizeClusterSummary`** is a new, separate, explicitly user-triggered action -- fired only by an in-panel "Synthesize summary" button that appears only when `canSynthesize` is true (at least one cached member, nothing synthesized yet) -- that IS allowed to call the LLM and write to cache, then push the result into the panel. This mirrors `refreshExplanationCommand.ts`'s existing "Regenerate" button precedent exactly: an explicit action separate from the panel's own automatic render path may generate; the render path itself never does.
- A `pinnedGraphRoot` field was added to `ExplanationPanelProvider` (distinct from `currentFunction`, which only tracks cursor-synced *explanation* views and is never touched by `showGraph`/pinning) so the in-panel "Synthesize summary" button can correctly retarget the pinned graph's own root, including when the graph was reached via a plain Command Palette invocation that never set `currentFunction` at all.
- A second `code-reviewer` finding on the same first draft: the synthetic row's invalidation hash was built from cached members' `fn_hash` values, which misses the case where a member regenerates with new `role_tag`/`one_liner` text (e.g. after a `PROMPT_VERSION` bump) while its *source* is unchanged -- `fn_hash` alone wouldn't change even though the text actually fed into the cluster's synthesis prompt did. Fixed by hashing each cached member's own row `cache_key` instead (Core Design Decision #2's full fn_source+context_hash+model_id+embedding_model_id+prompt_version tuple for that row), which changes whenever any of a member's real generation inputs change.
- A `notifySynthesizeFailed()`/`'synthesizeFailed'` message pair was added (mirroring session 58's `notifyRegenerateFailed` fix) so a failed `synthesizeClusterSummary` call (the `get_blast_radius` recompute can fail even though the synthesis call itself always resolves to a string) doesn't leave the "Synthesize summary" button stuck disabled with no fresh render message to reset it.

Additional decisions carried over from the original design, unaffected by the redesign:

- **Cluster selection is exactly `get_blast_radius`'s existing upstream walk, unmodified** -- no changes to `context.py` at all, reused read-only, per the session's own explicit out-of-scope list.
- **Synthesis input is restricted to the cluster's cached members only** (root, if cached, plus each upstream caller that already has a cache row) -- mirrors `summaryDocGenerator.ts`'s own per-function skip rule. An uncached member is never generated to fill a gap in.
- **Zero cached members anywhere → `canSynthesize: false`, no synthesis call possible at all** (not even via the explicit button, which doesn't render in this state) -- `synthesizeAndCacheClusterPurpose` also defensively no-ops if reached directly with nothing cached.
- **Synthetic cache row identity: `fn_id = ${root.fnId}::__cluster_summary__`**, appended directly to the root's own real fn_id rather than routed through `computeFnId(relFile, name)` like the file-summary row -- per-root-function granularity is required here. Confirmed safe against `functionResolution.ts`'s `assignFnIds`/`computeFnId`: a real fn_id only ever contains exactly one `::` separator, so a second one plus this reserved name can never collide with a real resolved function's fn_id.
- **`computeClusterSummaryFnHash` duplicates `computeFileSummaryFnHash`'s one-line body under its own name**, rather than sharing it -- consistent with this codebase's established "near-duplicate over premature shared abstraction for two call sites" precedent.
- **The docked-panel render is a flat member list, not depth-grouped "Level N" sections** like `renderGraph` (blast radius) -- reads better as a rollup, and visually differentiates the feature from a full graph browse.
