## Decisions made

### Design pass (per the session instructions, answered before implementation)

1. **Trigger:** automatic, right after `startIndexing()` finishes (sidecar connected, cache opened) — the same trust-gated moment as everything else, mirroring Session 2. No separate "start indexing" command. Re-running the full walk on every workspace open is not wasteful in practice: every entry does a local `cache.lookup()` first and only calls the sidecar on an actual miss, so a fully-cached repo just does cheap SQLite reads on the next open, not LLM calls.
2. **Throttling/cancelability:** the loop `await`s each `generateAndCache()` fully before scheduling the next one (never more than one generation in flight — the extension and the background pass share a single socket, and the sidecar's `_process_lines` dispatches strictly one line at a time, so overlapping writes would just queue behind each other anyway). A fixed 1s delay sits between iterations; because writes on the shared socket are dispatched in the order they arrive, that gap is a real window (not cosmetic) for a hover-miss/save-reindex/refresh request to get its write in and be served before the background pass's next request. A `CancellationTokenSource` is checked before each iteration; `lucidhover.cancelBackgroundIndexing` and `dispose()` (extension deactivate / window close) both cancel it, and the delay itself resolves early on cancellation rather than always waiting out the full second.
3. **De-duplication:** identical `cache.lookup()`-before-`generateAndCache()` pattern `SaveReindexManager` already uses — no second mechanism. A cache-miss race between the background pass and a concurrent save/hover/refresh is a pre-existing, already-accepted gap (nothing in Session 8 solved it either); not addressed here.
4. **Ranking order:** true function-level global order, not just file order — `list_ranked_functions` gives the whole repo's PageRank order up front, and the walk visits functions in exactly that order, only grouping by file to avoid re-opening/re-resolving the same document repeatedly.

### Matching tree-sitter def lines to VS Code's document-symbol lines
The sidecar's ranked list and VS Code's `executeDocumentSymbolProvider` are two independent sources of "where is this function," and (as already established for hover in `_find_def_tag`) they don't always agree exactly — e.g. `const foo = () => {}` arrow-function assignment spans. `matchRankedEntry` reuses the same tolerance: match by name within the file, then nearest start line. An entry that can't be matched at all (tree-sitter saw a def shape VS Code's symbol provider doesn't, or vice versa) is counted as `unresolved` and skipped rather than erroring the whole pass, mirroring `_handle_generate_explanation`'s existing degrade-rather-than-fail behavior for the same kind of resolution gap.

### 1s delay, chosen over a request-priority queue
Considered giving `SidecarManager.request()` real priority/preemption (e.g. a queue where interactive requests jump ahead of background ones), but the sidecar's Python dispatch loop is fundamentally synchronous and single-threaded — once a `generate_explanation` call is in flight, nothing can interrupt it regardless of what the extension host does, so a priority queue on the TS side can only affect the *order requests are written*, never preempt one already dispatched. A fixed inter-generation delay achieves the same practical effect (interactive requests get a real chance to be written and dispatched first) with far less code, and is consistent with the "reuse, don't build a second mechanism" instruction for this session.

### Manual verification steps for a human running this in VS Code

1. Open this folder in VS Code (trust the workspace if prompted). **Expected:** sidecar connects as in prior sessions (status bar message "LucidHover: sidecar connected"), then shortly after, a second status bar message "LucidHover: background indexing N functions..." (N should be the fixture repo's function count, 21 for `fixtures/sample-repo/repomap`, or your real repo's count if you're using one).
2. Open the LucidHover output channel and watch it while the background pass runs. **Expected:** a `background-index: starting (N functions ranked)` line, then one `background-index: generated <fn_id>` line per function that wasn't already cached (roughly 1s apart, per the throttle), finishing with a `background-index: done -- X generated, Y already cached, Z unresolved` summary line. `Z` should be 0 or very small for the fixture repo.
3. **This is the session's actual acceptance check.** Once step 2's summary line appears, hover over 5-10 functions you have not touched this session (pick ones from the output channel's `generated` lines). **Expected:** each shows its explanation immediately, and the output channel logs `cache hit for <fn_id> -- sidecar not invoked` for every one of them — **not** `cache miss ... requesting generate_explanation`. This is the direct proof that hover's cache-miss branch is now rare in practice for an indexed repo, per this session's actual goal.
4. While a background pass is still running (reopen the workspace, or use a bigger repo than the fixture so the pass takes longer than a few seconds), run the command palette → "LucidHover: Cancel Background Indexing" (`lucidhover.cancelBackgroundIndexing`). **Expected:** the status bar shows "canceling background indexing...", and within ~1s the output channel logs a `background-index: canceled -- X generated, Y already cached, Z unresolved` line (not `done`) and no further `generated` lines appear.
5. Run the same cancel command again when no pass is running (e.g. right after step 3/4 completes). **Expected:** status bar shows "no background indexing running", no error, no output channel line.
6. While the background pass is actively generating (mid-run, before it reaches a function you care about), hover over a function it hasn't gotten to yet. **Expected:** the hover still works (falls through to the pre-existing cache-miss synchronous generation path, exactly as before this session) — the background pass does not block or break interactive hover, it just means that function's explanation was generated by the hover request instead of the background pass. The output channel should show the hover's own `cache miss ... requesting generate_explanation` line interleaved with the background pass's lines, not queued indefinitely behind it (per the 1s throttle gap).
