## Decisions made
- **Heartbeat interval: 7s. Restart threshold: 3 consecutive failures** (so worst-case detection is ~21-28s after a real crash — one interval to notice the socket is dead, two more to confirm it's not a blip). Not specified precisely in the spec; chose 7s as a reasonable middle ground between "notices quickly" and "doesn't spam the process," and 3 failures so a single slow response (GC pause, etc.) doesn't trigger a needless restart.
- **Windows named pipes via `pywin32`, not `multiprocessing.connection`.** Confirmed empirically this session that `socket.AF_UNIX` is unavailable on this machine's Python build (`hasattr(socket, 'AF_UNIX')` is `False` even though Windows itself has supported `AF_UNIX` since 1803) — so a single `socket`-module implementation for both platforms wasn't available. `multiprocessing.connection`'s Windows pipe backend uses its own length-prefixed framing, incompatible with a raw newline-delimited stream read from a plain Node `net.Socket`. Used `win32pipe.CreateNamedPipe` in byte-stream mode (`PIPE_TYPE_BYTE`) instead, so both platforms speak the exact same wire format (`\n`-delimited JSON) — Node's `net` module needs no special-casing beyond the address string format.
- **`python` on PATH, no bundled interpreter/venv.** Matches how Session 3's `cli.py` was already being run manually. Provisioning (bundled venv vs. system Python) was explicitly deferred by Session 3's handoff and remains an open item — flagging again below, not resolved this session.
- **Malformed/unknown RPC requests return a JSON-RPC `error`, not a process crash.** `_dispatch()` in `rpc_server.py` catches `Exception` broadly around each handler call — this is a deliberate boundary catch (the request comes from a separate process over IPC, a real system boundary per CLAUDE.md's validation guidance), not defensive code for an internal case that can't happen. The heartbeat is the only thing that should ever trigger a restart, not an exception from a single bad request.
- **`index_file` returns every function in the file, not one function.** The task prompt said "accepts a file path ... returns the ranked context bundle as JSON," and the file is the natural unit for this session's proof (there's no cursor-position concept yet — that's the hover/panel wiring in later sessions). Implemented as: filter the file's tags to `kind == "def"`, call `get_function_context` for each, return `{file_path, functions: [...]}`.
- **Heartbeat timer is created once per `start()` and always cleared in `teardown()`** (not conditionally on `disposed`), so a restart doesn't leak a second interval on top of the still-running one from before the restart. Caught this in review before testing, not by observed misbehavior — noting because a naive "only clear on dispose" version would have silently double-fired heartbeats after every restart.

### Manual verification steps for a human running this in VS Code

1. Open this folder in VS Code (trust the workspace if prompted). **Expected:** an information message "Indexing paused — trust this workspace to enable LucidHover" does *not* appear (workspace is trusted); the status bar briefly shows "LucidHover: sidecar connected."
2. Open the "LucidHover" output channel (View → Output, select "LucidHover" from the dropdown). **Expected:** lines showing `spawning sidecar (address=...)`, `[sidecar] indexing ...`, `[sidecar] indexed N functions`, `[sidecar] listening on ...`.
3. Open Task Manager (or `Get-Process python`) and find the `python.exe` process spawned by VS Code. **Expected:** exactly one `python.exe` with a recent start time, no duplicates.
4. Run the command palette command "LucidHover: Debug Index Active File" with a `.js` file open (e.g. `fixtures/sample-repo/repomap/utils.js`). **Expected:** the output channel shows a `index_file(...) -> {...}` line listing that file's functions with `callers`/`callees` arrays; a status bar message confirms.
5. Kill the `python.exe` process from Task Manager (End Task) or `Stop-Process -Id <pid> -Force`. **Expected:** within ~1-2s, the output channel logs `sidecar process exited (code=..., signal=...)`, then `heartbeat failed (1/3): ...`.
6. Wait roughly 15-20 more seconds without touching anything. **Expected:** two more `heartbeat failed (n/3)` lines, then `sidecar unresponsive -- restarting`, `spawning sidecar (...)`, and `sidecar restarted successfully`. A new `python.exe` PID appears in Task Manager.
7. Re-run "LucidHover: Debug Index Active File." **Expected:** it succeeds again (proves the reconnect, not just the respawn, works).
8. Close the VS Code window (or run "Developer: Reload Window" then close). **Expected:** the `python.exe` process disappears from Task Manager within a couple seconds — no orphan left behind.
