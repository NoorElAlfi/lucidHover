## Decisions made
- **Primary-path selection is "highest-importance confident successor" at each hop**, per the session brief's own explicit instruction — not shortest-path, not first-declared, not caller-count. Reuses the exact same PageRank `self.importance` values `get_function_context`/`get_blast_radius` already read (Core Rule 3: no new ranking machinery).
- **Cycle handling mirrors `get_blast_radius` exactly**: if the chosen next node is already on the path, the closing edge is still recorded as a real graph fact, but the walk stops there without adding a second node or re-expanding. Verified live: mutual recursion `a()`↔`b()` rooted at `a` produces `nodes=[b]`, `edges=[(a,b),(b,a)]`.
- **`direction: 'downstream'` on the existing `GraphViewPayload` type is the render-mode discriminator**, not a new payload shape or a new webview message type — the webview's existing `'renderGraph'` message handler now branches to `renderTrace()` for `'downstream'` and keeps `renderGraph()` for `'upstream'`. This was already anticipated in session 45's own type/docstring (`direction: 'upstream' | 'downstream'` was defined then, unused until now), so no type change was needed here.
- **`SHOW_CALL_TRACE_COMMAND_ID` lives in `explanationPanelProvider.ts`, not `callTraceCommand.ts`** — same reasoning session 45 already established for `SHOW_BLAST_RADIUS_COMMAND_ID` (the panel's own webview message handler needs the id to fire the command; `callTraceCommand.ts` needs to import the graph-view types from the panel module either way, so defining the id there too avoids a circular import).
- **`showCallTrace`/`registerShowCallTraceCommand` split, from the start** (not discovered mid-session this time, since session 45 already hit and documented this exact issue) — the integration test calls `showCallTrace(...)` directly rather than through the command registry, since `extension.ts`'s own activation already registers the real command id once in the Extension Development Host every integration test runs inside.
- **`enrichNodes`/`closestResolved`/`toGraphViewEdges` in `callTraceCommand.ts` are near-duplicates of `blastRadiusCommand.ts`'s** — not extracted into a shared helper. Consistent with the established pattern from session 45 (per-feature isolation over a shared abstraction two call sites don't yet justify); `code-reviewer` confirmed this call was already made and didn't re-flag it.
