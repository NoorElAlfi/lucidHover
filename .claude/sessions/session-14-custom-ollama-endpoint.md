## Decisions made

Answering the five design questions from the session brief, in order:

1. **Configuration surface: two independent settings, `lucidHover.modelId` and `lucidHover.ollamaEndpoint`.** The spec's own Tech Stack row ("Optional upgrade LLM: Local Ollama endpoint, `qwen3:8b` or `qwen3.6:27b`") and LLM Backend Strategy section ("user-supplied local Ollama endpoint") name both the model and the endpoint as user-facing, so both get a setting. No combined "profile" abstraction — nothing in the spec asks for named presets, and Core Rule 8 warns against adding scope beyond what's asked.
2. **Scope: both generation and embeddings redirect to the custom endpoint.** The two daemons-with-different-models-pulled trap named in the session brief is real, and `EMBEDDING_MODEL_ID`'s own doc comment already ties it to "the same local backend MODEL_ID's generation calls already use" — splitting them would contradict that existing assumption. `repo_map.ollama_base_url` is read by both `_handle_generate_explanation` and `_query_retrieved_chunks`/the startup embedding pass.
3. **Endpoint URL is spawn-time, `model_id` stays per-request.** `model_id` already worked per-request with no design change needed. The endpoint can't follow the same path because the startup embedding pass needs it before any RPC request exists (same reasoning `EMBEDDING_MODEL_ID` already established) and per decision #2 both tiers must share one value. Applying a changed setting requires either a full window reload or the new explicit `lucidhover.restartSidecar` command — built this session (a small, ~15-line addition reusing the existing private `restart()` teardown-and-`start()` path that heartbeat-failure recovery already relies on) rather than leaving "reload the window" as the only option, since a feature whose entire point is switching backends easily would be poor UX if the only way to apply it were a full extension reload.
4. **No settings-time validation ping.** `ollama_client.py`'s `_post()` already raises a clear, actionable `OllamaError` ("Cannot reach Ollama at ..." / "Run: ollama pull ...") that already surfaces through the existing `generate_explanation`/`reindex_file` RPC error paths (per `_handle_generate_explanation`'s own comment: "never silently stub or fall back... surface it as a clear JSON-RPC error"). Adding a synchronous ping at settings-change time would mean a new blocking network call from the extension host with no existing precedent for where that's allowed to happen outside the sidecar's own request loop — not worth the complexity for a case the existing error path already covers once the user actually tries to use the misconfigured endpoint.
5. **No full-repo re-walk on model switch.** Every hover/save/flush/git-hook naturally regenerates on its own cache miss once `resolveModelId()` starts returning the new value — same mechanism as any other cache miss, no new code path. `BackgroundIndexManager`'s startup walk is untouched; a future session could explicitly wire "trigger a background walk after a settings change" if the natural regeneration pace turns out to feel too slow in practice, but nothing in the spec asks for it and Session 13's artifact already flagged the general pattern of not pulling in background-walk scope without an explicit decision.

Additional decisions not covered by the five questions:
- **Local-only enforcement is TS-side only, not duplicated in Python.** The extension host is the only thing that ever constructs the sidecar's spawn argv; the sidecar has no settings surface of its own to protect. Single-sourcing the loopback check avoids two copies drifting apart.
- **Loopback allowlist is strict: `localhost`/`127.0.0.1`/`::1` only, not private/LAN IP ranges.** The spec's own language is "local endpoint" (matching the existing hardcoded `localhost:11434`), not "any network-reachable Ollama instance" — accepting LAN IPs would be a real scope judgment call the spec doesn't make, so this session took the narrower, unambiguous reading. Caught during implementation: `URL#hostname` renders IPv6 loopback as `[::1]` (with brackets), which the first version of `isLoopbackHost` compared against bracket-less `::1` and would have wrongly rejected — fixed before this was ever exercised live, confirmed by a standalone Node script exercising representative inputs (cloud URL, LAN IP, IPv6, malformed, uppercase host, missing scheme) with the exact accept/reject table in "Test status" below.
- **Rejection surfaces once, at the two places that resolve the endpoint** (`startIndexing()` and the restart command), via a shared `resolveOllamaEndpointAndWarn()` helper in `extension.ts` — not inside `resolveOllamaEndpoint()` itself, which stays a pure decide-only function so it doesn't need a `vscode.window`/output-channel dependency just to report.

## Deviations from spec

- None against the spec text. The `lucidhover.restartSidecar` command isn't explicitly named anywhere in the spec, but is a direct, minimally-scoped consequence of decision #3 above (a spawn-time setting needs *some* way to apply without a full reload) rather than new milestone scope.

## Blockers / open questions

- **`resolveOllamaEndpoint`'s loopback allowlist has no automated regression test** (see "Test status" -- checked via a throwaway Node script, not committed). If a TS test harness gets set up in a future session (Build Order step 17), porting that input/output table into a real test would be worth doing then.
- **Whether the strict `localhost`/`127.0.0.1`/`::1`-only allowlist is too narrow for real usage** (e.g. someone running Ollama in a container reachable only via a LAN or Docker-bridge IP) is an open product question, not a bug -- the spec doesn't discuss it either way, so this session took the narrower reading (see "Decisions made"). Live verification (step 5 above) exercised the accept path with a real loopback port, not a LAN-IP rejection case, since that's the same code path already covered by the input/output table in "Test status."
