Extracted the inline spawn/wire logic from `start()` into a new `spawnChild(address, interpreterIndex)` method, driven by a new `SPAWN_INTERPRETER_CANDIDATES = ['python', 'python3']` constant: on an ENOENT from the current candidate, retries with the next candidate using the same address (so `connectWithRetry`'s already-in-flight poll picks up whichever candidate actually starts `rpc_server.py`, no separate restart needed) instead of failing immediately. Only the *last* candidate's failure is recorded as `lastSpawnError` for `classifyStartFailure()` (session 53) to read. The common/working case (`python` present) pays zero extra cost — the fallback only fires on an actual ENOENT.
- [src/extension/__tests__/suite/sidecarManager.test.ts](../../src/extension/__tests__/suite/sidecarManager.test.ts) — 2 new tests: the python→python3 fallback succeeding, and both candidates ENOENT-ing still classifying as `spawn-failed` from the last candidate's own error message. Updated the pre-existing "give-up toast" test's `spawnStub.callCount` assertion from `5` to `10` (`MAX_RESTART_ATTEMPTS × SPAWN_INTERPRETER_CANDIDATES.length`) since that test's stub ENOENTs on every call, so every restart attempt now spawns twice before giving up on that attempt — a correct consequence of the fix, not a regression. The other MAX_RESTART_ATTEMPTS test (line ~218) is unaffected — its stub never emits a spawn error, so the fallback path never triggers.
