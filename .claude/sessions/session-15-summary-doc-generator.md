## Decisions made

Answering the five design questions from the session brief, in order:

1. **Trigger: one new explicit command, `lucidhover.generateSummaryDocs`.** Registered unconditionally like every other command (Core Rule 6), but only acts once `workspaceRoot`/`cache`/`sidecar` are all non-null (same readiness gate `refreshExplanationCommand.ts` already uses). Not automatic after background indexing finishes — writing real files to the workspace is a new category of side effect this extension has never had before (confirmed: nothing before this session writes to the workspace filesystem), so it needs a real, separate user action, not a side effect of something else completing.
2. **Per-file purpose-paragraph caching: reuse `ExplanationCache`, synthetic `fn_id`, no new table.** `fn_id = computeFnId(relFile, '__file_summary__', 0)` — `__file_summary__` is a reserved name VS Code's document-symbol provider can never produce, so it can never collide with a real function's `fn_id`, and neither hover/panel/CodeLens/gutter nor `BackgroundIndexManager` can ever accidentally surface it (they all look up by real resolved symbols or walk `list_ranked_functions`, which only returns real def tags). Its `fn_hash` is the new `computeFileSummaryFnHash` — a hash of the sorted set of that file's *current* real function hashes, computed without duplicating any logic already in `hash.ts` (it's a new one-line pure function living right next to `computeCacheKey`, not a copy of it). Cache key reuses `computeCacheKey` unchanged, passing the surrogate hash through the existing `fnSource` slot and `''` for `contextHash` (there's no sidecar context-bundle step for this call, unlike per-function generation) — under the new `SUMMARY_DOC_PROMPT_VERSION`, not `PROMPT_VERSION`, since bumping one prompt's version shouldn't force the other prompt's cached rows to regenerate.
3. **Trigger-to-doc mapping: no new tracking.** Docs are only ever as fresh as the last explicit run of the command — confirmed sufficient per the brief's own framing. At run time the command re-reads whatever's currently in `ExplanationCache` for every function (same `list_ranked_functions` + `resolveFunctionsInFile` + nearest-match pattern `BackgroundIndexManager` already uses), so a run always reflects the latest state regardless of which trigger (save/flush/git-hook/background-index) produced it. The per-file synthetic cache row is purely an LLM-call-avoidance optimization across repeat runs of the doc command itself, not a staleness model — none of the three trigger managers were touched or taught anything about file-level output, per the brief's explicit instruction not to change how they work.
4. **Output layout: `docs/wiki/index.md`, `docs/wiki/functions.md` (top 25 by importance), `docs/wiki/<relFile>.md` per file — full overwrite of only those known filenames each run.** "Module" is treated as equivalent to "file" for this session — the fixture repo (and the spec's own examples) show no directory-level rollup requirement, and building a separate module/directory grouping on top of file-level pages would be scope the spec doesn't ask for (Core Rule 8). Overwrite is a plain full rewrite of the generator's own known files (`index.md`, `functions.md`, and one page per file with cached functions) — nothing else under `docs/wiki/` is enumerated, touched, or deleted, so a user's own hand-added files there survive a re-run untouched; this reads as sufficient protection against clobbering without building diff/preservation logic the spec never asked for.
5. **Failure handling: per-file, not whole-run.** A `generate_file_summary` failure for one file is logged to the output channel and that file's page is still written, using the template content plus a placeholder note ("purpose paragraph unavailable — see the LucidHover output channel") instead of the paragraph; the run continues to the next file and reports a final aggregate count. Matches the brief's own reasoning: this is "a command over their whole repo," where losing every already-computed page over one file's Ollama hiccup would be a worse experience than per-function generation's existing fail-loudly-it's-one-hover behavior.

Additional decisions not covered by the five questions:
- **Skip-visibility logging, added after live manual verification (see Test status).** The user's first live run of Step 4 showed 24 functions in `functions.md` against a repo the sidecar itself logs as having 26 -- correct behavior (2 were unresolved, the same tree-sitter/document-symbol drift `BackgroundIndexManager` already tolerates), but the generator gave no clue why, silently `continue`-ing past both the "not yet cached" and "unresolved" skip cases. Added two counters and one aggregate output-channel line (`summary-docs: skipped N of M ranked function(s) (X not yet cached, Y unresolved...)`), only emitted when non-zero -- same "log only when there's something to say" precedent `StaleTracker`'s `flagStaleDependents` already sets. Not a new staleness/tracking mechanism, just visibility into a gap this session's own manual test surfaced.
- **No confirmation dialog before writing files.** Writing markdown files into the user's own workspace, triggered by a command the user explicitly invoked by name ("Generate Summary Docs"), is the same class of already-precedented action as "Refresh Explanation" writing cache rows without a confirmation prompt — the command name itself is the user's explicit authorization, not a side effect requiring separate confirmation.
- **`docs/.gitignore`/commit question: untouched, exactly as instructed.** Nothing in this session's code reads or writes `.gitignore`, and no commit is made — the spec's "user chooses" is left entirely to the user.
- **New code appended, not inserted, into `prompt.py` and `config.ts`.** Both files have uncommitted, still-unmerged work in `task_e56c43ff`'s worktree touching specific regions (`FEW_SHOT_EXAMPLES`/field-rules text in `prompt.py`, the `PROMPT_VERSION` doc-comment block in `config.ts`). This session's additions live at the end of each file, in a new function/constant, so a future merge of that task's branch should apply cleanly.

4. Open `functions.md`. **Expected:** a markdown table of up to 25 functions repo-wide, sorted by importance, each row linking back to its file's page. **Confirmed** -- showed 24 (of the repo's 26 total), root-caused as 2 unresolved functions, not a bug; see above.
5. Run **LucidHover: Generate Summary Docs** a second time immediately. **Expected:** completes noticeably faster than the first run (per-file purpose paragraphs served from cache, not regenerated) — check the LucidHover output channel for `list_ranked_functions`/no new `generate_file_summary` errors; content should be unchanged. **Confirmed.**
6.
