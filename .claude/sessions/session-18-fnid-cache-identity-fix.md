## Decisions made

1. **Root-cause fix (new fnId scheme), not a "detect-and-carry-forward" patch in the three trigger loops.** The task description offered both as open options. Chose the identity-scheme fix because: (a) it makes fnId genuinely line-invariant by construction rather than self-healing-after-a-delay, so a hover on a freshly-shifted function still hits cache immediately instead of needing a save/flush/git-hook pass to repair it first; (b) it requires zero changes to `saveReindex.ts`/`backgroundFlush.ts`/`gitHookReindex.ts` — they already do `cache.lookup()` then `generateAndCache()` on miss, and just stop missing spuriously; (c) it doesn't reintroduce the orphaning problem it's supposed to fix (a "carry forward under new fnId" patch still needs to run on every single edit that shifts lines, whereas removing line from identity means there's usually nothing to carry).
2. **Identity = enclosing-scope-qualified name, not a raw line number or a content hash.** Nesting (which class/function a symbol lives inside) is what actually distinguishes two same-named functions — not where they currently sit in the file. This also fixes a second, related bug in the same family: previously, two functions with the same bare name in *different* scopes (e.g. two classes each with a `constructor`) could theoretically collide if VS Code's document-symbol line numbers ever matched, or diverge unpredictably as either sibling shifted — qualified-name identity handles this correctly and predictably.
3. **`#n` disambiguation only applies to genuine duplicate qualified names** (e.g. two accidental identically-named top-level function declarations, or two identically-named methods in the same class), assigned in document order. This is a much rarer edit (inserting/removing a same-named duplicate above another) than "any line added anywhere earlier in the file," which is what made the old scheme spuriously reassign nearly every fnId in a file on almost every edit.
4. **Accepted a one-time full-cache invalidation as the cost of the fix.** Every existing row's `fn_id` was in the old `relFile::name::line` format; after this change, `cache.lookup()` will miss for every function once (until the next trigger regenerates it), even ones whose line never moved. This has direct precedent in this project: Session 11's `EMBEDDING_MODEL_ID` change is documented in `cache/config.ts` as deliberately invalidating every existing row for the same reason (an identity/versioning correctness fix outweighs a one-time regeneration cost). No migration/backfill logic was added for old-format rows — per the project's "don't build unrequested backwards-compatibility machinery" default, and because the cache already has no eviction mechanism at all (per the task's own note that `cache_key` is the PK, not `fn_id`, so nothing has ever evicted stale rows) — old-format rows become simply unreachable dead rows, same fate the *already-orphaned* rows from the pre-fix bug have today. Flagged as a possible future GC pass in "Handoff," not built here (Core Rule 8 — out of scope for this fix).
5. **Did not touch `generateAndCache`'s sidecar request payload** (`line: target.range.start.line` sent to `generate_explanation`), `computeCacheKey`, or any prompt/context logic — explicitly out of scope per the task, and this value is only used sidecar-side for context-window purposes, not identity.

1. Open `fixtures/sample-repo` (or `B:\LucidHover` with the workspace trusted) with the sidecar running, and let background indexing finish caching `repomap/handlers.js`'s functions (hover each of `validateAndPersistSignup`, `handleSignupRoute`, `retryQueueWorker` once if needed to force-populate the cache). **Expected:** each hover eventually shows an explanation.
2. Note the current LucidHover output channel content, then edit *inside* `validateAndPersistSignup`'s body to add one new line (e.g. a comment) without touching `handleSignupRoute` or `retryQueueWorker`, and save. **Expected:** the `save-reindex: ...` summary line shows `validateAndPersistSignup` regenerated (its content changed) but `handleSignupRoute` and `retryQueueWorker` counted as **unchanged (skipped)** — before this fix, both would have been silently regenerated despite no edit to either.
3. Hover `handleSignupRoute` and `retryQueueWorker` again. **Expected:** output channel logs `cache hit for repomap/handlers.js::handleSignupRoute -- sidecar not invoked` / `...retryQueueWorker...` (new fnId format, no `::<line>` suffix) — not a fresh `cache miss` line.
