- [src/extension/cache/explanationCache.ts](../../src/extension/cache/explanationCache.ts) — added `getCurrentRowForFnId()`: a read-only query (fn_id + model/embedding/prompt ids, no fn_hash filter, ordered by `generated_at DESC`) that finds the row that was most recently "live" for a given fnId regardless of hash. This is how a trigger tells a brand-new function (no prior row) apart from a confirmed content change (a prior row exists, under a different `fn_hash`) — only the latter can make some *other* cached function's row stale. - [src/extension/saveReindex.ts](../../src/extension/saveReindex.ts), [src/extension/backgroundFlush.ts](../../src/extension/backgroundFlush.ts), [src/extension/gitHookReindex.ts](../../src/extension/gitHookReindex.ts) — each of the three triggers that already call `reindex_file` + hash-diff + `generateAndCache` now also: (1) checks `getCurrentRowForFnId()` before regenerating, to classify the regeneration as "brand new" vs. "confirmed change"; (2) calls `flagStaleDependents()` once per file after processing it, for whichever functions turned out to be confirmed changes; (3) clears `StaleTracker` for every fnId actually regenerated this pass, as a final guard step *after* all `flagStaleDependents` calls (see "Decisions made" #4 — self/mutually-recursive edges). ## Decisions made

1. **Staleness detection is scoped to the three triggers that already call `reindex_file` (save, periodic flush, git-hook)** — not `BackgroundIndexManager`'s startup/workspace-open full walk. The session brief's own phrasing anchors staleness work to triggers that "already contact the sidecar (`reindex_file`, `generate`)"; `BackgroundIndexManager` calls `generate_explanation` directly off `list_ranked_functions` and never calls `reindex_file` per function, so extending it would mean adding a new sidecar-contact pattern, not reusing an existing one. Flagged as a known, narrow gap (see "Blockers").
2. **"Confirmed dependency changed" = a prior cache row existed for that fnId (any hash) and the newly generated row has a different `fn_hash`.** Distinguished via the new `ExplanationCache.getCurrentRowForFnId()`, which deliberately omits the `fn_hash` filter `lookup()` uses. A brand-new function (no prior row at all) never flags dependents stale — nothing about a dependency actually *changed* the first time it's generated.
3. **Silent lazy regen vs. visible badge (spec's Open Items, explicitly this session's to resolve): visible badge.** The spec's own dirty-vs-stale language already presumes something is displayed ("cached explanation *may be wrong*" implies the user needs to be told), and Core Design Decision #5 ("never silently regenerate") rules out the other option outright — a stale row is never regenerated on its own, only ever displayed differently until an explicit trigger (save/flush/git-hook naturally reaching it, or manual refresh) actually regenerates it.
4. **`dirty` takes precedence over `stale` when a function is somehow both.** A function currently being hand-edited (dirty) is a stronger, more immediate signal that the shown explanation may not match the code than "some other function changed" (stale) — no need to show both at once, and showing "dirty" is never wrong when it's also stale (the dependency-change fact doesn't disappear, it's just superseded in priority for display).
5. **The docked panel does not repeat the freshness badge.** Explicitly confirmed against the design-question list: the spec's Hover UX table describes the panel as levels-1-2 *content* (why_it_exists/used_by/calls/side_effects/risk_note), not a freshness surface — the hover header is the one and only place freshness is shown, matching the spec's existing "Hover header always shows role tag + freshness" line (which this session's badge now actually implements in full, past the v0 placeholder it names).
6. **Staleness is per-function only, keyed by fnId, matching `DirtyTracker`'s exact shape** (`Map<relFile, Set<fnId>>`) — no file-level rollup. Nothing in the spec or design questions calls for one, and CodeLens/gutter (a separate concern, explicitly not touched this session) are the only other surfaces that operate at file scope.
7. **State lives in a new in-memory `StaleTracker`, not a SQLite column.** Mirrors `DirtyTracker`'s own already-established pattern exactly (in-memory, cleared on extension restart, no schema migration) rather than writing a stale flag into cache rows — writing into the cache table would mean updating rows never touched by generation, which would also spuriously fire `ExplanationCache`'s `onDidWrite` listeners (CodeLens/gutter redraw), which is out of scope for this session (CodeLens/gutter role-badge logic is explicitly not to be touched).
8. **A self- or mutually-recursive function must not be immediately re-flagged stale by its own regeneration.** Caught during this session's own review, not in the original design questions: if function A calls itself (or A and B call each other) and both get regenerated in the same trigger pass, `flagStaleDependents` would otherwise mark the *just-regenerated* function stale again via its own call-graph edge. Fixed by deferring every `StaleTracker.clearFnId()` call for functions regenerated this pass to *after* all `flagStaleDependents` calls for that pass complete (not immediately after each individual `generateAndCache` call) — for `BackgroundFlushManager`/`GitHookReindexManager` this guard spans the *entire tick/marker-processing pass* (all files), not just one file, since a dependency edge can cross files within the same pass.

## Blockers / open questions

- **Live VS Code verification: done, in a follow-up conversation after this artifact was first written.** The manual steps above were run against `fixtures/sample-repo` and confirmed the fresh/dirty/stale badge, cross-file stale propagation, and manual-refresh clearing all work as designed — *with one caveat found during that run*, see next bullet.
- **Found live: a pre-existing quirk in `computeFnId`'s line-embedded identity (src/extension/cache/hash.ts:8) can mask the stale badge.** `fnId = relFile::name::startLine` bakes an absolute line number into cache identity. Editing a function shifts the start line of every function *after* it in the same file, giving them new fnIds and making their `cache.lookup()` miss — so they get silently regenerated (a real LLM call) in the very same save pass, even though their own source never changed. This predates Session 13, but Session 13 makes the consequence directly visible: a function `flagStaleDependents` just marked `stale` can have that flag immediately wiped by this session's own recursion guard (Decision #8), because the guard can't tell "regenerated because it's genuinely a dependent of another cyclic function in this batch" apart from "regenerated because its line number spuriously shifted." Confirmed live: editing a line inside `validateAndPersistSignup` in `repomap/handlers.js` (which has `handleSignupRoute`/`retryQueueWorker` defined after it in the same file) caused those two to show `fresh` instead of the expected `stale`; a same-line-count edit (no shift) showed `stale` correctly, confirming the diagnosis. Not fixed this session (out of scope: touches the fnId identity scheme, not the badge display logic) — flagged as a separate background task (`task_b6af2bfc`) for a future session to scope properly.
- **`BackgroundIndexManager`'s startup/workspace-open full walk does not participate in staleness detection** (Decision #1). In the narrow case where that walk regenerates a function whose `fn_hash` changed since a previous session (e.g. the file was edited by another tool between VS Code sessions), any other cached function depending on it will not be flagged stale until save/flush/git-hook next touches the *changed* function's file. Low-probability edge case (background-index's main job is filling in never-before-cached functions), not fixed this session — would require adding a `reindex_file` call into a per-function background-index path that doesn't currently make one.
- **`getCurrentRowForFnId()` can return a row generated under a *previous* model/embedding/prompt version if the current tuple has never generated this fnId before, but an older tuple has — no, actually it correctly filters on the current model/embedding/prompt tuple**, so this isn't a real gap; noting it here only because it was the one edge case double-checked during this session's own design pass (see cache class's doc comment) and worth a future session confirming stays true if the cache-key formula ever changes shape again.
