## Decisions made
- **Language: JavaScript**, not Python. VS Code's built-in TypeScript/JavaScript language service supplies `vscode.executeDocumentSymbolProvider` results with zero extra dependencies. Python has no bundled document-symbol provider in core VS Code — it needs the separate Python/Pylance extension, which would make this session's pass/fail depend on the tester's installed extensions rather than on the code itself. Revisit language choice explicitly when tree-sitter parsing lands (Build Order step 3) — that's a hard requirement regardless of this session's choice.
- **Function-boundary detection uses `vscode.executeDocumentSymbolProvider`, not tree-sitter.** Tree-sitter is explicitly a later step (Build Order step 3 — Aider repomap port). For this session, the built-in JS language service's symbol tree is enough to prove `registerHoverProvider` + span detection works end-to-end.
- **`const foo = () => {...}` detection is a heuristic.** The built-in JS language service reports these as `SymbolKind.Variable`, not `Function`, so `isFunctionLike()` additionally accepts `Variable` symbols whose `detail` string matches `/=>|\bfunction\b/` (the inferred type signature TS attaches to the symbol). This is intentionally approximate — good enough for throwaway scaffolding, not a substitute for the real parser coming in step 3.
- Hover walks the full nested `DocumentSymbol` tree (recursing into `children`) so hovering inside the nested `increment` function in `makeCounter` resolves to `increment`, not the outer arrow function — validates that span detection handles closures reasonably before real parsing exists.
