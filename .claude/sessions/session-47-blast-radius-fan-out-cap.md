## Decisions made
- **Measured first, per the session's own instruction and sessions 28/29/33's precedent.** Indexed real pokerogue (6,633 functions) and ran `get_blast_radius` at the existing `max_depth=3` against 8 real high-fan-in functions (`getPokemonNameWithAffix`, `queueMessage`, `unshiftNew`, `resolve`, `getUi`, `playSound`, `applyAbAttrs`, `getMaxHp`). Before any cap: 363-494 total nodes and 241-8,772 total edges per function -- a real, observed problem, not a hypothetical one. After the cap: bounded to at most 45 nodes (3 levels × 15) and dramatically fewer edges (61-526) for the same functions, confirming both that the problem was real and that the fix works at real-repo scale.
- **Reused `CALLER_CALLEE_CAP`'s value (15) as `BLAST_RADIUS_LEVEL_CAP`**, not a new number. Same "how many related functions to show a human" judgment call `get_function_context`'s single-hop callers/callees already makes; users are already used to that convention, and nothing in the measurement suggested a different number was warranted.
- **Cap applied per level, not globally**, per the session's explicit instruction -- a global cap across the whole walk would silently bias toward whichever depth happens to be visited first. At 3 levels this bounds the walk to at most 45 nodes.
- **Omitted candidates are dropped from both `nodes` and `edges`** at the depth that omits them, not just from `nodes` -- an edge into an omitted candidate would just reproduce the same unbounded-edges problem the cap exists to fix (confirmed by measurement: edges shrank far more than nodes once this was applied, e.g. `getPokemonNameWithAffix`'s edges went from 8,536 to 261).
- **A once-omitted node is permanently excluded for the rest of the walk** (tracked via a new `omitted_ever` set, separate from `visited`) -- see Deviations below; this was not the original design and was added mid-session after code-reviewer found the gap.
- **Omission reporting is a plain `{depth, omitted_count}` list, not a dense depth-indexed structure** -- only depths that actually omitted something get an entry, matching the existing `callers_omitted`/`callees_omitted` single-hop convention's spirit (a count, not a truncated-but-hidden list).
- **UI surfaces the omission as a plain note under the relevant "Level N" section** ("+N more not shown"), not a new affordance -- per the session brief's explicit instruction, reusing the existing `addParagraph`/`empty-state` pattern already used for other secondary notes in the same renderer.

## Deviations from spec
- **A real correctness bug was found by the first code-reviewer pass and fixed mid-session, not part of the original design.** The initial implementation only added *kept* candidates to `visited`; an *omitted* candidate was left untracked entirely. If that same omitted node also happened to be a direct predecessor of one of that depth's *kept* nodes (a second, indirect/longer edge into the walk), it would be "rediscovered" as a brand-new candidate at the next depth, potentially win a cap slot there, and get recorded at the wrong (deeper) depth -- with its true, shorter edge silently replaced by the longer indirect one. This broke the function's own documented invariant ("a node is recorded once, at the depth it was first reached... BFS guarantees that's its shortest upstream distance"), which held under the original unconditional-BFS design (session 45) but broke once per-level capping was introduced. Fixed by adding a permanent `omitted_ever` set (separate from `visited`) that `new_callers` is filtered against at every subsequent depth, so a once-omitted node can never resurface as a node or an edge again, however it's reached. A second, narrowly-scoped code-reviewer pass confirmed the fix closes the bug with no new issues (see Test status).
