## Decisions made

1. **Dirty-tracking is keyed by `fnId`, not `fn_hash`.** `fn_hash` is a hash of the function's *current* source, so it changes on every keystroke that touches the function — flagging "this exact hash is dirty" would already be stale before the next keystroke lands. `fnId` (relFile+name+line) is the stable slot every other trigger and the cache already key on, and it's what periodic flush actually needs to know which function to re-check.
2. **Periodic flush's scope is the dirty set, not a full repo re-walk.** Per the session brief's explicit instruction ("must walk only dirty-flagged functions, not a full re-walk"), each tick groups dirty fnIds by file, calls `reindex_file` once per dirty file, then only hash-diffs/regenerates the specific fnIds that were flagged — not every function in that file (unlike `SaveReindexManager`, which does hash-diff every function in a saved file, since a save is a stronger, whole-file signal than a few keystrokes).
3. **`backgroundFlushIntervalSeconds` default = 25.** The spec's trigger table already gives a range ("~20-30s"); the Open Items list flagged only the *exact* default as unresolved. 25 is the midpoint — a concrete number within the range the spec already committed to, not new scope. Configurable, minimum 5s in the `package.json` schema to prevent a pathologically tight loop.
4. **A flush-cycle generation failure leaves the fnId dirty (auto-retry next cycle) rather than clearing it.** `SaveReindexManager`/`GitHookReindexManager` both log-and-move-on on failure with no retry, but periodic flush is the one trigger that runs on its own schedule regardless of user action — leaving a failed fnId dirty means a transient sidecar/Ollama hiccup self-heals on the next tick once whatever caused it clears up, instead of silently dropping the pending change until the next save.
5. **Git-hook signaling mechanism: marker file (`.git/LUCIDHOVER_REINDEX`) + `FileSystemWatcher`**, matching the plausible shape named in the session brief. The hook computes the diff itself (`git diff --name-only <old> <new> -- '*.js'`) via one shared, LucidHover-owned script (`lucidhover-git-reindex.sh`) that all three hook types call with a resolved old/new ref pair — `post-commit`/`post-merge` use `HEAD@{1}` vs `HEAD` (reflog), `post-checkout` uses git's own `$1 $2` args, gated on `$3 = 1` (branch-level checkout only — see Deviations).
6. **"Hooks are appended, never overwritten" applies to the three hook entry points (`post-checkout`/`post-merge`/`post-commit`), not the shared diff script.** The shared script is exclusively LucidHover's own file — nothing else would ever write to `lucidhover-git-reindex.sh` — so it's safe to unconditionally rewrite on every install, while the three real hook files (which husky, pre-commit, or a hand-written script might already occupy) get a marker-guarded, idempotent append that preserves whatever was already there.
7. **Install policy: prompted opt-in**, confirmed with the user via `AskUserQuestion` before writing anything to `.git/hooks/`, per the session's explicit instruction. This also matches the spec's own "Handling Active Development" Notes line ("offered opt-in on first activation in a repo") more closely than either of the two options named in the Open Items list (silent-automatic-with-opt-out, or command-only with no prompt at all). A decline is remembered per-workspace (`workspaceState`) but not permanent — `lucidhover.installGitHooks` re-offers it.
8. **The pure git-hook-file-manipulation logic was pulled into its own `vscode`-free module (`gitHookInstaller.ts`)** specifically so it could be unit-tested with plain `node` against a real temp git repo (see "Test status") — this is the one piece of this session's work that edits files potentially owned by another tool, so getting the idempotent-append logic actually verified (not just reasoned about) mattered more here than for the rest of the session's TS, which still has no test harness (see Blockers).

## Deviations from spec

- **`post-checkout` only re-indexes on a branch-level checkout (`$3 = 1`), not a file-level one (`git checkout -- <path>`, `$3 = 0`).** Git doesn't hand the hook enough information in the file-level case to know which files were touched (no old/new tree to diff against — the working tree already matches `HEAD` for whatever was checked out). Documented as a known gap rather than solved: a file-level revert like this will be caught by the next save, periodic flush (once the user edits it further), or a manual refresh instead. Verified live in a scratch repo that this case correctly no-ops rather than doing something wrong (see "Test status").
- Everything else matches the spec's trigger table and this session's pre-approved design (dirty-tracking → flush → git-hook, all still gated through the existing hash-diff-then-regenerate check).
