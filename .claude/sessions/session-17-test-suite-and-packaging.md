## Decisions made

Answering the design questions from the session brief, in order:

1. **Framework: Mocha + sinon + `@vscode/test-electron`**, per Core Rule 3 — the officially-documented VS Code pattern, not Jest or a custom harness. The integration suite uses Mocha's TDD interface (`suite`/`test`/`setup`/`teardown`), matching VS Code's own extension-testing convention; the plain-Node unit suite uses BDD (`describe`/`it`) since it's a wholly separate Mocha instance with no such convention to match.
2. **Split**: only `cache/hash.ts` and `cache/explanationCache.ts` were vscode-free before this session (confirmed by scanning every import in `src/extension/`). Extracted a third vscode-free module this session (`cache/ollamaEndpoint.ts`) for the same reason `debounce.ts` already was one — testable loopback/URL-parsing logic without needing the Extension Development Host. Everything else that imports `vscode` runs in the `@vscode/test-electron` integration suite.
3. **SidecarManager strategy**: originally planned to `sinon.stub(child_process, 'spawn')`/`sinon.stub(net, 'connect')` directly. That failed in this Electron host (`TypeError: The descriptor for property 'spawn' is non-configurable and non-writable`) — discovered via the test-runner subagent's first pass, not anticipated in the design pass. Fixed with constructor-injected `spawnFn`/`connectFn` (default to the real functions) instead of fighting the platform. `EventEmitter`-based fakes simulate crash/exit/connect-failure; the give-up/backoff test uses **real timing** (not `sinon.useFakeTimers()`) after weighing the risk of faking global timers inside a live, shared Extension Host process (VS Code's own UI runs on the same event loop) against the cost of ~55 real seconds for one test — real timing won on safety/determinism grounds; the ~55s cost is paid once per full suite run, not per iteration of a tight dev loop.
4. **The pipe-quoting bug**: root cause confirmed to be the old throwaway harness building the pipe path as a shell command string, not anything in `rpc_server.py`. Fixed by using `subprocess.Popen` with an argv list (`shell=False`) and `pywin32`'s `win32file` for the Windows client side — same technique `sidecarManager.ts`'s own `cp.spawn` already uses, same API `rpc_server.py`'s `_serve_windows` already uses. Verified: the new test passes in ~2s.
5. **Coverage bar**: targeted the repeatedly-flagged gaps — cache-key/hashing (unit), Workspace Trust wrapper correctness (integration, basic — full untrusted-workspace sidecar-gating end-to-end is still only covered by session-02's original verification, since headless integration launches with `--disable-workspace-trust`), hover's cache-hit-never-touches-sidecar guarantee (integration), and the SidecarManager recovery loop (integration, the main new coverage: 5 tests covering spawn argv, crash→recovery, dispose-doesn't-restart, stale-exit-is-ignored, and give-up→manual-restart-unsticks). Deliberately did **not** add heartbeat-driven-restart-triggering coverage (same `restart()` code path as the exit-driven trigger already covers; would need either real 21s+ of heartbeat-interval waiting or the same fake-timer risk already avoided elsewhere) or any CodeLens/gutter/staleness-badge/summary-doc UI coverage — not chasing 100%, per the brief.
6. **Packaging dry-run**: added `@vscode/vsce` as a devDependency, ran `vsce package` with no other changes. Measurement only, no fix (Core Rule 8) even though the fix (a `.vscodeignore`) is easy to see. `vsce package` succeeded with just warnings (missing `repository` field, missing LICENSE, no `.vscodeignore`) — no `publisher` field was required to package locally (only warnings), so no manifest fields were added just to unblock this.
