## Decisions made

### Docked panel placement: Activity Bar container, not a declared Secondary Side Bar location
The spec's Hover UX table says the docked panel is "registered in the Secondary Side Bar." Checked this directly: package.json's declarative placement for the Secondary Side Bar (`contributes.viewsContainers.secondarySideBar` / the `contribSecondarySideBar` API) is **still proposed-only** as of the newest VS Code (1.106) — confirmed via VS Code's own issue tracker (microsoft/vscode#264346) before writing any package.json. Core Rule 2 forbids proposed APIs, so this can't be used, for the same reason Core Design Decision #11 already ruled out the Hover Verbosity API.

Resolved (confirmed with the user before implementing, same pattern as Decision #11): register the panel as its own `viewsContainers.activitybar` container instead. VS Code's "Move View → Secondary Side Bar" is a native, stable, user-driven action available on any view regardless of its declared home — so the spec's intent (a persistent docked panel, ideally in the secondary sidebar) is fully reachable, just via user action instead of a forced declarative placement. Documenting this here since it's a real deviation from the letter of the spec's table, not just an implementation detail.

### Panel reveal mechanism: the view's auto-generated `<viewId>.focus` command
"Show more →" needs to both (a) make the panel visible if it's hidden/uncreated, and (b) show the specific hovered function, which may not be wherever the text cursor currently sits (mouse hover position and cursor position are independent). Used VS Code's auto-generated `lucidhover.explanationPanel.focus` command (generated automatically for every contributed view since ~1.62, stable) to reveal/create the view, then `ExplanationPanelProvider.showRow(row)` to push content explicitly by `cache_key` — bypassing cursor-based resolution entirely for this one push. If the view hasn't been resolved yet when `showRow` is called, the row is stashed in `pendingRow` and flushed once `resolveWebviewView` actually runs (which the `.focus` call triggers). After that one explicit push, `onDidChangeTextEditorSelection` takes over normal cursor-sync — the user doesn't need to click "Show more" again for subsequent functions, per the session's recommended default-open behavior.

### Cursor-sync resolution reused from the hover path, not duplicated
Both surfaces need "what function is under this position" using the exact same fn_id/fn_hash logic the cache key depends on. Extracted this into `functionResolution.ts` rather than letting the panel re-derive it independently, which would risk the two surfaces disagreeing about identity for the same cursor position.

### Panel is strictly cache-only, gated on visibility
`ExplanationPanelProvider.onSelectionChanged` returns immediately unless `this.view?.visible` is true — selection-change events fire on every cursor move, but resolving symbols + hitting the cache is wasted work if nobody can see the result. This mirrors Core Rule 4's "hover is a cache lookup only" for the second surface: the panel never calls `sidecar.request(...)`; a cursor on an uncached function just shows an empty-state message ("hover it to generate one") rather than triggering generation.

### `used_by`/`calls` navigation: workspace symbol search, no persisted index
The schema's `used_by`/`calls` are bare names, not locations. Per the session instructions ("no separate lookup index needed yet"), resolution happens at click time via `vscode.executeWorkspaceSymbolProvider(name)` — the same built-in language-service command that powers "Go to Symbol in Workspace" — filtered to function-like `SymbolKind`s, first match wins. No new index/table was built. This is same-repo by construction (the workspace symbol provider only searches open workspace files), matching the v0 scope note.

### Small addition beyond the spec's exact field list: a function-name header in the panel
The spec's Hover UX table lists the panel's content as exactly `why_it_exists, used_by, calls, side_effects, risk_note`. Added one more thing not in that list: a plain function-name header at the top of the panel (no `role_tag`, no `one_liner` — those stay hover-only). Without it, a cursor-synced panel showing only prose fields gives no way to tell which function is currently displayed, especially right after the cursor moves. This isn't a schema field, so it doesn't interact with the "empty fields render as nothing" rule; flagging it here as a deliberate, minimal addition rather than letting it pass silently.

## Deviations from spec
- **Panel is not registered in the Secondary Side Bar via a declarative package.json location** — see "Docked panel placement" above. This is the one real deviation from the Hover UX table's literal wording; functionally reachable by the user via native VS Code UI, not by extension code.
- Panel header shows the function name (not in the spec's field list for the panel) — see "Small addition" above. No schema fields were added or reinterpreted.
